# PPT 장르 4종 — 목적이 다르면 조립 논리가 다르다

포맷이 `wide-16x9`·`short-9x16` 둘뿐이던 동안 **PPT 는 전부 영상 씬 스틸의 부산물**이었다.
슬라이드 수 = 씬 수였고, 한 화면 한 메시지라는 영상 규율이 그대로 슬라이드가 됐다.
읽는 자료를 만들 수 없었던 이유는 무대 크기가 아니라 **조립 논리**였다 — 영상 조립기는
씬 수를 골격(skeleton) 길이로 고정한다.

이 문서는 장르 4종의 차이를 정리하고, 그중 **문서형** 조립기의 규칙과 실측을 남긴다.
구현은 `src/wdpipeline/scenario.py` 의 `assemble_doc_scenario`, 검증은
`tests/test_scenario_doc.py`(21건)다.

## 1. 4장르 비교

| | **발표 16:9** | **세로 숏폼** | **문서형** | **A4 인쇄** |
| --- | --- | --- | --- | --- |
| 포맷 id | `wide-16x9` | `short-9x16` | `deck-doc-16x9`·`deck-4x3` | `print-a4` |
| 무대 | 1920×1080 | 1080×1920 | 1920×1080 · 1440×1080 | 1240×1754 |
| 목적 | 발표자가 말로 채우는 화면 | 소리 없이 넘기는 피드 | **읽는 사람이 혼자 이해** | 인쇄·회람 |
| 분량 정본 | 초 (`duration`) | 초 (`duration`) | **장수 (`slides`)** | 장수 (`slides`) |
| 규격 | 90s(실측 78s)·7씬 | 60s·5씬 | 15장(5~30)·12장(5~24) | 10장(5~20) |
| 모션 | 있음 (진입 애니메이션) | 있음 | **없음** (정지 화면) | 없음 |
| 낭독 | 켬 (5.5자/초) | 켬 | **끔** | 끔 |
| 밀도 | 한 화면 한 메시지 | 한 화면 한 문장 | **불릿 3~6 + 근거 1** | 좌동 |
| 씬 수를 정하는 것 | skeleton 길이(고정 7) | skeleton 길이(고정 5) | **보고서 분량(가변)** | 보고서 분량 |
| 조립 논리 | 조각 → 7역할 슬롯 배치 | 조각 → 5역할 슬롯 배치 | **페이지 → 섹션, 근거 1개 → 슬라이드 1장** | 좌동 |
| 구조 payload | 슬롯 1개를 두고 경쟁 | 대부분 못 실림 | **경쟁 없음** (근거마다 슬라이드) | 좌동 |

핵심은 마지막 두 줄이다. 영상은 **골격이 먼저 있고 조각이 그 자리를 두고 겨룬다.**
문서형은 **보고서 구조가 먼저 있고 슬라이드가 거기서 태어난다.** 그래서 문서형에서는
"흐름도 3건 중 1건만 화면에 오른다" 같은 탈락이 원리적으로 없다.

## 2. 문서형 조립 논리

```text
cover(1) → toc(1) → [ section(1) → body(1~3) ] × 페이지 수 → summary(1)
```

| 단계 | 규칙 |
| --- | --- |
| 섹션 경계 | **원 보고서의 페이지 1장 = 섹션 1개.** 페이지 이름의 선두 번호("1. ")는 떼고 쓴다 |
| 소절 경계 | 페이지 안의 `heading` 블록이 소절을 연다 (`_page_segments`) |
| 본문 슬라이드 | **구조 블록(표·수치·도식) 1개 = 본문 슬라이드 1장.** 페이지당 최대 3장 |
| 근거 없는 소절 | 독립 슬라이드가 되지 못하고 **앞 슬라이드의 불릿으로 흡수**된다 (버리지 않는다) |
| 근거가 없는 페이지 | 그 페이지의 **소절 구성표**(소절명·항목 수)를 근거로 세워 본문 1장을 만든다 |
| 목차 | 섹션 목록에서 자동 유도. 섹션이 하한(4)에 못 미치면 본문 단위로 내려가 `group`(섹션명)으로 묶는다 |
| 표지 | 제목·작성일·분류(태그)·구성(절 수·장수·근거 건수) — 읽는 자료의 표지는 서지사항이 본체다 |
| 요약 | `ai_summary` 우선, 없으면 **절마다 최상위 claim 하나씩**(confidence 만으로 고르면 5줄이 한 절에서 나온다). 각 줄의 `note` 는 출처 절 이름. **행동(actions)은 지어내지 않는다** — "원문 N페이지 전문 확인", "미수록 근거 N건 원문 대조"처럼 검증 가능한 것만 |
| 길이 | 씬 `nat_default` 합을 그대로 쓴다. 포맷 허용대를 벗어날 때만 `duration.target` 으로 균일 스케일 |
| 상한 방어 | `ScenarioDoc.scenes` 50 초과가 예상되면 ① 페이지당 본문 수를 줄이고 ② 그래도 넘으면 뒤 섹션을 빼고 목차에 "외 N개 항목은 원문 참조"로 밝힌다 |

### 근거 슬롯 매핑 (`doc-body.evidence`)

`tpl.doc-body` 계약은 근거 종류를 `table | chart | image` 3종으로 못박았고 표는 3열×5행,
막대는 5개가 상한이다(실측 역산, 모듈 schema.json). 조립기는 **용량 상수를 코드에 두지 않고
schema.json 의 maxItems/maxLength 를 읽는다** — 템플릿이 폭을 다시 재면 조립도 따라간다.

| 원문 payload | 근거 kind | 대표 선별 | 잃는 것 · 남기는 것 |
| --- | --- | --- | --- |
| `table` | table | 행 첫·끝 표본(`_span_indices`) | 4열 이상은 앞 3열만 — `source` 에 "원문 6열×8행 중 3열×5행" |
| `series` 단일 | chart | 값 극단 + 중앙값(`_extreme_indices`) | 앞 N개 절단 금지. 0 기준선 강제, 강조 막대 1개 |
| `series` 다계열 | table | 계열×항목 공통 축 격자 | 값이 빠진 항목은 0 으로 지어내지 않고 제외 |
| `graph` (flow) | table | 순서 표본 | 화살표를 잃고 `#·단계·비고` 행으로 — `note` 는 유지 |
| `graph` (tree/network) | table | 얕은 레벨 우선(`_level_indices`) | 엣지를 잃고 `항목·층` 행으로 |
| `pairs` | table | 순서 표본 | `항목·값` 2열 — 영상 경로처럼 한 줄로 뭉개지 않는다 |
| `timeline` | table | 순서 표본 | `일자·항목·상태` 3열 |
| `media` | (미배선) | — | `evidence.image` 슬롯은 있으나 자산 채널 연결이 아직 없다 |

무언의 절단은 하지 않는다. 실은 만큼과 원문 규모를 `source`(≤30자)와 `takeaway`(≤44자)에
반드시 적는다 — "원문 3열×33행 중 3열×5행", "외 2건 근거는 원문 참조".

## 3. 실측 (`examples/reportarchive/report_sample.json` · 5페이지 63조각 12구조블록)

같은 입력을 세 장르로 조립해 비교했다 (`tests/test_scenario_doc.py`).

| | 발표 16:9 | 세로 숏폼 | **문서형** |
| --- | --- | --- | --- |
| 슬라이드/씬 | 7 | 5 | **18** (표지1+목차1+섹션5+본문10+요약1) |
| 총 길이 | 90.0s | 60.0s | 136.0s (장당 체류 명목 — 규격 아님) |
| 수용 문안 | 1,797자 | 668자 | **4,352자** (발표 대비 2.4배) |
| 구조 payload 도달 | 75.0% (9/12) | 0.0% (0/12) | **100.0% (12/12)** |
| 구조 payload 배치 | 58.3% (7/12) | 0.0% | **83.3% (10/12)** |
| 미배치 사유 | 슬롯 경쟁 탈락 | 세로 5역할에 근거 슬롯 없음 | 페이지당 본문 3장 상한(page 5 의 5건 중 2건) |

세부 판정(`slot_fit_report`).

```text
문서형 tally  ok 2 · trim 1 · summarized 7 · split 2 · none 0   reach 100.0%  placed 83.3%
발표    tally  ok 0 · trim 3 · summarized 2 · split 4 · none 3   reach  75.0%  placed 58.3%
```

`strict_reach_pct`(ok+trim 만)는 양쪽 다 25.0% 다 — **슬롯이 좁은 것은 문서형도 같다.**
달라진 것은 "받을 슬롯이 아예 없어 사라지던 3건(none)이 0 이 됐다"는 점과, 같은 payload 가
개별 행으로 실린다는 점이다.

### 33행 위젯 카탈로그 표 — 같은 표, 두 장르

| | 발표 16:9 | 문서형 |
| --- | --- | --- |
| 도착 슬롯 | `proof.cases` (근거 카드 1칸) | `doc-body.evidence.table` (전용 슬라이드 1장) |
| 전략 | `group` — 카테고리별 **건수**로 전 행을 대표 | `span` — 개별 행 첫·끝 표본 |
| 화면에 남는 것 | "텍스트 5 · 표 4 · 차트 6 …" 집계 한 줄 | `텍스트 / heading / 섹션 제목` 같은 **실제 행 5줄 × 3열** |
| 생략 표기 | 배지 "8군 전수 집계" | `source` "원문 3열×33행 중 3열×5행" + split 힌트 7장 |

집계는 전 행을 대표하지만 개별 행을 보여주지 못하고, 표본은 개별 행을 보여주지만 전체를
대표하지 못한다. **읽는 자료에서는 후자가 맞다** — 독자가 원문을 열 수 있기 때문이다.

## 4. 문서형 심의 프리셋 초안

포맷의 `presets.deliberation` 에 넣을 초안이다. `format.yaml` 은 임무 A 소유라 여기 문서로만
남긴다 — 첫 제작 심의가 끝나면 회의록에서 그대로 옮기면 된다(PLAN §8.0 승격 루프).

### 장르별 심의 의제가 갈리는 지점

| 장르 | 심의의 첫 쟁점 |
| --- | --- |
| 발표 16:9 | **발표자가 무엇을 말할 것인가** — 화면은 말의 보조다. 씬당 한 메시지 |
| 세로 숏폼 | **3초 안에 넘길 사람을 어떻게 잡는가** — 후킹·자수·엄지 가림 |
| 문서형 | **읽는 사람이 누구인가 · 훑어보기 경로 · 근거 배치** (아래) |
| A4 인쇄 | 위 + **한 장으로 떼어 회람될 때도 성립하는가** (쪽별 자립성) |

### `presets.deliberation` 초안 (문서형)

```yaml
presets:
  deliberation:
    type: scenario_build
    participants:
      - narr-story-architect      # ST — 섹션 분할·소절 병합 설계 (scenario_patch 독점 작성권)
      - narr-copywriter           # CP — 불릿 42자·요약 40자 안에서 집필
      - ux-audience-advocate      # AU — 독자 재정의·훑어보기 경로 검수
      - vis-dataviz               # DV — 근거 슬롯 배정 (표/막대/도판 중 무엇으로 실을지)
      - vis-layout-grid           # LG — 좌 불릿 / 우 근거 2열 밀도 판정
      - qa-consistency            # QC — 생략 표기(외 N행·N건) 누락 감시
    agenda:
      - "독자 — 이 덱을 혼자 읽는 사람은 누구인가. 발표자가 없다는 전제가 문안 밀도·근거 배치를 전부 바꾼다"
      - "훑어보기 경로 — 표지→목차→섹션 간지만 넘겨도 논지가 서는가. 목차 항목은 섹션명 그대로가 맞는가"
      - "근거 배치 — 페이지당 본문 3장 상한에서 어느 근거를 세울지. 밀린 근거는 takeaway 에 명시됐는가"
      - "환원 손실 — 흐름도·계층을 표로 내릴 때 잃는 형태가 논지를 해치지 않는가 (해치면 도판으로 승격)"
      - "생략 정직성 — 원문 규모(N열×M행)와 실린 양이 source 에 다 적혔는가. 무언의 절단 0건"
      - "분량 — slides 허용대 안인가. 넘치면 섹션을 줄일지 페이지당 본문을 줄일지"
```

낭독 예산·구간 예산(`dur_plan`)은 **문서형에 없다.** 모션도 낭독도 없어 시간이 규격이
아니기 때문이다. 대신 `slides{target,min,max}` 가 그 자리를 대신한다.

`copy_guide` 는 조립기가 이미 `doc-*/schema.json` 의 maxLength 를 직접 읽으므로,
프리셋에 옮길 때는 **심의가 실제로 부딪힌 항목만** 적는 편이 낫다(전량 복사는 이중 관리다).
실측 상한은 다음과 같다.

| 슬롯 | 상한 | 슬롯 | 상한 |
| --- | --- | --- | --- |
| `cover.title` | 34자 | `body.title` | 30자 |
| `cover.meta[].value` | 26자 | `body.bullets[].text` | 42자 (3~6개) |
| `toc.items[].text` | 26자 (4~10개) | `body.evidence.caption` | 26자 |
| `toc.items[].note` | 18자 | `body.evidence.table` | 3열 × 5행 (셀 10자) |
| `section.name` | 20자 | `body.evidence.chart.bars` | 5개 (라벨 14자) |
| `section.lead` | 54자 | `summary.points[].text` | 40자 (3~5개) |
| `section.points[]` | 16자 (≤4개) | `summary.actions[].text` | 34자 (1~4개) |

## 5. 알려진 어긋남

> §5.1 은 **해소됐다** — 세 포맷의 `template_pool` 1순위가 `tpl.doc-*` 로 배선됐고,
> 실산출로 확인했다(§6). 아래 원문은 경위 기록으로 남긴다.

1. **포맷 배선 한 줄이 남았다.** 씬 템플릿 쪽은 다 됐다 — `modules/scene-templates/doc-*/`
   5종이 `module.yaml`·`schema.json`·registry 등록까지 갖췄고 `formats: [deck-doc-16x9,
   deck-4x3, print-a4]` 를 선언한다. 반면 `formats/{deck-doc-16x9,deck-4x3,print-a4}/format.yaml`
   의 `template_pool` 은 아직 전부 `native.*`(exporter 가 텍스트로 조립)다. 조립기의 문서형
   경로는 골격 역할의 1순위 템플릿이 `tpl.doc-*` 일 때 발동하므로(`is_doc_format`), 현행
   3포맷으로는 켜지지 않는다.

   ```yaml
   template_pool:            # 지금
     cover: [native.cover]
     ...
   template_pool:            # 씬 경로를 켜려면
     cover: [tpl.doc-cover]
     toc: [tpl.doc-toc]
     section: [tpl.doc-section]
     body: [tpl.doc-body]
     summary: [tpl.doc-summary]
   ```

   `native.*`(파워포인트에서 곧바로 고쳐지는 텍스트 슬라이드)와 `tpl.doc-*`(캡처 씬)는
   같은 문서 구조의 두 렌더 전략이라 **둘 다 남겨도 된다** — 역할 풀에 순서대로 적으면
   1순위가 이긴다. 어느 쪽을 1순위로 둘지는 포맷 소유자의 판단이다.
   검증은 **실물 모듈 + `template_pool` 만 뒤집은 format.yaml** 로 수행했다
   (`tests/test_scenario_doc.py::_format_specs`) — 저 한 줄이 뒤집히는 순간 그대로 실사용 경로다.
2. **막대 근거가 실제 덱에 안 실렸다.** report_sample 5페이지는 구조 블록 5건 중 4번째가
   `progress_bar` 라 페이지당 3장 상한에 밀렸다. 선택 규칙이 **문서 순서 우선**이라
   생긴 결과다(장르 원칙상 순서를 흔들지 않았다). 종류 다양성을 우선할지는 심의 쟁점이다.
3. **`evidence.image` 미배선.** 도판은 `collect_media` 자산 채널로 흐르는데 문서형 조립기가
   아직 그 채널을 읽지 않는다. `slot_fit_report` 는 media 를 `none` 으로 계상한다.
4. **표 3열 상한의 정보 손실.** 6열 RACI 는 앞 3열만 남는다. 어느 3열을 남길지는 현재
   문서 순서 고정이다 — "코드값 열 우선" 같은 규칙은 심의 확정 뒤에 넣는 편이 낫다.
5. **A4 는 조립기가 구분하지 않는다.** `print-a4` 와 `deck-doc-16x9` 는 문서형 조립 논리가
   같고 무대·자수만 다르다. 쪽별 자립성(한 장씩 떼어 회람) 요구가 확정되면 그때 갈라야 한다.

## 6. 4장르 실산출 실증 (2026-07-29)

§3 은 **조립 단계**(ScenarioDoc)의 수치였다. 이 절은 그것을 끝까지 밀어 **파일로 나온
PPTX 를 열어 잰** 수치다. 입력은 같은 `examples/reportarchive/report_sample.json` 하나,
산출·스크립트는 `data/ppt_genres/`(README 참조), 대표 슬라이드는 `data/quality_compare/ppt/` 다.

`format.yaml` 의 `outputs` 가 실제로 분기를 지배한다 — 문서형 3종은 `wda render` 가
mp4 를 **시도조차 하지 않고** `[render] mp4 생략 — 포맷 deck-doc-16x9 산출 pptx` 를 찍는다.

### 6.1 장르별 실측 규격

| 장르 | 포맷 | 슬라이드 | 슬라이드 규격 | 무대 px | image KB | hybrid KB |
| --- | --- | --- | --- | --- | --- | --- |
| 발표용 가로 | `wide-16x9` | **7** | 13.333×7.500in (12192000×6858000 EMU) | 1920×1080 | 1719.4 | 1200.6 |
| 세로 숏폼 | `short-9x16` | **5** | 7.500×13.333in | 1080×1920 | 1213.5 | 903.5 |
| 문서형 덱 | `deck-doc-16x9` | **18** | 13.333×7.500in | 1920×1080 | 1132.1 | **112.7** |
| 4:3 덱 | `deck-4x3` | **18** | 10.000×7.500in | 1440×1080 | 1125.2 | 133.1 |
| A4 인쇄물 | `print-a4` | **18** | 8.270×11.690in (7562000×10689000 EMU) | 1240×1754 | 1133.5 | 133.7 |

슬라이드 수 = 씬 수는 유지되지만, **문서형은 씬 수를 보고서가 정한다** — 5페이지 보고서가
표지1+목차1+섹션5+본문10+요약1 = 18장을 낳았다(§2 조립 논리). 발표용 7장은 골격 길이다.

hybrid KB 가 문서형에서 **10배 작다**(1132 → 113KB). 글자를 빼고 나면 문서형 배경은
거의 단색이라 PNG 압축이 극단적으로 잘 먹는다. 발표용은 카드·그림자·노드 그래프가 남아
1200KB 다. 배포 파일 크기로 보면 문서형 hybrid 가 압도적으로 유리하다.

### 6.2 밀도 — "문서형이 실제로 밀도가 높은가"

hybrid 모드로 뽑아 **슬라이드에 실제로 그려진 글자**를 python-pptx 로 추출해 셌다
(`data/ppt_genres/density.json`).

| 장르 | 장 | 총 글자 | 장당 글자 | 장당 항목(텍스트 상자) | 장당 글자 범위 | 폰트 pt |
| --- | --- | --- | --- | --- | --- | --- |
| 발표용 가로 | 7 | 1,664 | **237.7** | **18.1** | 75~350 | 12.0~56.0 |
| 세로 숏폼 | 5 | 651 | 130.2 | 11.2 | 82~206 | 16.0~160.0 |
| 문서형 덱 | 18 | **4,338** | **241.0** | **21.3** | 111~433 | 12.0~54.0 |
| 4:3 덱 | 18 | 4,338 | 241.0 | 21.3 | 111~433 | 12.0~54.0 |
| A4 인쇄물 | 18 | 4,338 | 241.0 | 21.3 | 111~433 | 11.5~51.9 |

**발표용 대비 배수 — 장당 글자 1.01배, 장당 항목 1.18배, 덱 전체 글자 2.61배, 전체 항목 3.02배.**

솔직히 적는다. **장당 밀도는 발표용과 사실상 같다(1.01배).** 본문 슬라이드만 비교해도
문서형 312.1자 vs 발표용 299.4자(1.04배)다. 문서형의 이득은 장당 밀도가 아니라
**덱 전체 도달량(2.61배)과 구조**에서 나온다.

왜 장당이 안 늘었나 — 슬롯 상한은 충분히 넓은데 조립기가 안 채운다.

| 장르 | 장당 실측 자수 | 장당 스키마 상한 | **채움률** | 본문 슬라이드만 |
| --- | --- | --- | --- | --- |
| 발표용 가로 | 237.7 | 409.1 | **58.1%** | 5장 · 299.4/483.2 = 62.0% |
| 세로 숏폼 | 130.2 | 205.8 | 63.3% | 3장 · 161.7/244.3 = 66.2% |
| 문서형(3무대 공통) | 241.0 | **669.5** | **36.0%** | 11장 · 312.1/906.2 = **34.4%** |

`tpl.doc-body` 한 장의 자수 상한은 **929자·48슬롯**으로 영상 최대 템플릿(`proof` 616자·23슬롯)의
1.5배, 영상 평균(409자·22슬롯)의 2.3배다. 그런데 실제로 실린 것은 상한의 3분의 1이다.
**밀도의 병목은 템플릿이 아니라 조립기의 채움 전략이다.**

지면 점유로 봐도 같은 결론이다 — 텍스트 상자 면적 비율 발표용 14.7% vs 문서형 16.4%(A4 11.7%),
잉크(배경 아닌 픽셀) 비율은 오히려 발표용 7.23%가 문서형 4.16%보다 높다. 발표용의 잉크는
카드·필·그래프 장식이고 문서형의 잉크는 대부분 글자라, **같은 잉크면 문서형이 더 많은 글자**이지만
지면 자체가 비어 있다.

### 6.3 시각 비교 — 문서형이 읽는 자료답게 보이는가

대표 슬라이드 3장씩을 `data/quality_compare/ppt/{포맷}/` 에 저장했다(image 모드 PPTX 에
박힌 슬라이드 PNG 원본 그대로).

**보인다 — 골격은 명백히 읽는 자료다.**

- **표지**(`deck-doc-16x9/01-표지.png`) — 제목·부제 아래 서지 4항목(작성일 2026-05-27 ·
  구성 5개 절·18장 · 분류 3태그 · 근거 표·수치 10건)이 2열로 놓이고 "원문 5페이지 · 내부 참고용"이
  각주로 붙는다. 발표용 오프닝(로고+한 줄 배지)에는 없는 층이다.
- **목차**(`02-목차.png`) — 번호·항목·리더 점선·**쪽번호**(3/6/9/11/14)가 실제 섹션 슬라이드를
  가리킨다. 영상 덱에는 목차라는 개념 자체가 없었다.
- **본문**(`08-본문-표.png`) — 좌 불릿 6줄 + 우 근거 카드(3열×5행 표 + "원문 4열×5행 중 3열×5행"),
  머리에 킥커·**쪽번호 8/18**, 발에 꼬리말(문서명·날짜). 발표용 개념 슬라이드가 노드 그래프 +
  요약 3줄인 것과 정반대 방향이다.

**안 보이는 것 — 지면을 못 채운다.** 16:9 문서형 본문은 콘텐츠가 상단 약 50%에서 끝나고
하단 절반이 빈다. A4 는 더 심해 상단 40%만 쓴다. 4:3 이 그나마 가장 꽉 찬다(자/Mpx 155.0 vs
16:9 116.2 vs A4 110.8) — 자수·항목 상한을 **가장 좁은 무대 기준으로 역산**한 설계라
가장 넓은 무대에서 여백이 남는 구조다.

**표 셀 절단이 눈에 띈다.** 셀 상한 10자 · 헤더 6자라 실제 화면에 `게시…` `참조…`
`ReportMou…` `원본 작성자 +…` 처럼 잘린 셀이 줄줄이 남는다. 근거로 세운 표가 근거 구실을
못 하는 구간이다(§6.5 후속 과제).

### 6.4 하이브리드 편집성 — 왕복 확인

문서형 덱을 `mode="hybrid"` 로 뽑아 python-pptx 로 열고, 고치고, 저장하고, 다시 열었다
(`data/ppt_genres/scripts/editability.py` → `editability.json`).

| 항목 | 결과 |
| --- | --- |
| 텍스트 프레임 | image 모드 **0개** → hybrid **383개** (18장, 장당 21.3개) |
| 슬라이드 수·크기 | 18장 · 13.333×7.500in — 두 모드 동일 |
| 그림 | 슬라이드당 정확히 1장(배경) |
| 배경에서 글자가 빠졌는가 | 18장 합 **618,657px** 변화, **텍스트 상자 밖 0px** |
| 왕복 편집 | 제목 `보고서 관계 3종 비교` → `…(수정본)`, 표 셀 `ReportMou…` → `ReportMount` — 재오픈 후 둘 다 유지 |
| 부작용 | 상자 이동 **0개**, 폰트·크기 전부 보존, 상자 수 32 → 32 |
| 한글 폰트 지정 | `a:latin` 395 · `a:ea` 395 (동수 — 파워포인트 한글 폴백 방지) |

"상자 밖 0px"이 핵심이다. 배경에서 사라진 픽셀이 전부 텍스트 상자 안이라는 뜻 —
표 괘선·카드·필·리더 점선은 하나도 건드리지 않았다.

부수 소득이 하나 있다. **조립기가 자수 상한 때문에 자른 표 셀을 사람이 파워포인트에서
되살릴 수 있다** — `ReportMou…` → `ReportMount` 왕복이 그 실증이다. 자동 조립의 절단이
최종 확정이 아니라 초안이 된다.

### 6.5 남은 격차

**① 4:3 은 실제로 된다 — 단, 새 템플릿으로만.**

무대 경계를 넘는 요소를 DOM 에서 직접 재어(장식 블리드 제외) 판정했다
(`stage_overflow.json`). 씬별 스틸 시각 0.9 지점 측정.

| 템플릿 | 무대 | 넘친 씬 | 최대 넘침 |
| --- | --- | --- | --- |
| 영상 가로 `tpl.*` | 1920×1080 (원 무대) | 0 / 7 | 0.0px |
| 영상 가로 `tpl.*` | 1440×1080 (4:3) | **5 / 7** | **320.0px** |
| 영상 가로 `tpl.*` | 1240×1754 (A4) | **5 / 7** | **520.0px** |
| 문서형 `tpl.doc-*` | 1920×1080 | **0 / 18** | 0.0px |
| 문서형 `tpl.doc-*` | 1440×1080 | **0 / 18** | 0.0px |
| 문서형 `tpl.doc-*` | 1240×1754 | **0 / 18** | 0.0px |

가로 템플릿 재사용 기각은 독립 재현됐다 — 깨지는 5씬(문제·개념·절차·차별점·실증)과
살아남는 2씬(오프닝·클로징)이 `formats/deck-4x3/format.yaml` 의 lessons 와 정확히 일치한다.
넘침 폭도 무대를 줄인 만큼 그대로다(1920−1440=480 중 310~320px, 1920−1240=680 중 510~520px).
반대로 문서형 템플릿은 세 무대 전부 0px다 — **한 벌의 코드가 세 무대를 탄다**는 설계 주장이
실물로 확인된다.

QA 게이트도 5장르 전부 통과했다(`gates.json`) — error 0 · warn 0, 5빌드 합계 위반 0건.
게이트 4(최소 폰트)·5(넘침)·3(대비)·7(frame-match)가 A4·4:3 무대에서도 걸리지 않는다.

**② 문서형이 아직 못 담는 위젯.** `slot_fit_report` 를 5포맷에 돌린 결과(`slot_fit.json`).

| 원문 위젯 | 규모 | 발표용 판정 | 문서형 판정 |
| --- | --- | --- | --- |
| comparison | 5 | **none**(탈락) | ok |
| table | 2 | **none**(탈락) | ok |
| raci_matrix | 8 | **none**(탈락) | summarized |
| flowchart ×3 | 6 | trim ×3 (2건 미배치) | **summarized ×3** |
| key_value ×2 | 9·8 | split | **summarized ×2** |
| tree | 15 | summarized | split (5행만) |
| table | 33 | summarized | split (5행만) |
| progress_bar | 7 | split | summarized · **미배치** |

도달률은 문서형 100%(12/12) vs 발표용 75%(9/12), 배치율 83.3% vs 58.3%로 §3 과 같다.
그러나 **12건 중 7건이 `summarized`** — 도달했지만 위젯의 형태가 표 몇 줄로 환원됐다는 뜻이다.
구체적으로 못 담는 것은 셋이다.

- **도식(flowchart 3건 전부).** `doc-body.evidence` 가 `table|chart|image` 택1이라 화살표·분기가
  표 행으로 눕는다. 문서형에 **도식 슬롯이 없다**.
- **4열 이상 표(raci_matrix 8, 원문 최대 6열).** 3열 상한에 앞 3열만 남는다.
- **막대(progress_bar 7).** `chart.bars` 5칸 상한을 넘고, 페이지당 본문 3장 상한에도 밀려
  **덱에 아예 안 실렸다**(placed False). 5장르 통틀어 실제 덱에 차트 근거가 0건이다 —
  이번 산출의 근거 슬롯은 전부 표다.

**③ 필요한 후속 템플릿.** 위 격차에서 바로 나온다.

| 후보 | 채우는 구멍 | 근거 |
| --- | --- | --- |
| `tpl.doc-diagram` (도식 전면) | flowchart·tree·network 를 형태째 | 3건이 표로 환원, 문서형 유일한 무손실 실패 |
| `tpl.doc-table` (표 전면, 6열×12행급) | 4열 이상·장행 표 | raci 6열 → 3열, 33행 → 5행 |
| `tpl.doc-chart` (차트 전면) | 계열·막대 6개 이상 | progress_bar 7 미배치, 덱 차트 0건 |
| `tpl.doc-body-dense` (2단 본문·불릿 10줄급) | 16:9 하단 절반 공백 | 채움률 34.4%, 자/Mpx A4 110.8 |
| `tpl.doc-appendix` (부록 표 연속) | split 힌트가 요구한 장수(33행 → 7장) | 지금은 힌트만 나오고 장이 안 생긴다 |

**④ 표 셀 자수 상한이 실사용을 막는다.** 셀 10자·헤더 6자는 4:3/A4 우열 내폭(491/413px)
역산값인데, 한글 데이터에서 `게시…`·`ReportMou…` 처럼 **식별 불가한 절단**이 된다.
전면 표 템플릿(위 ②)이 나오기 전까지는 열 수를 3에서 2로 줄여 셀 자수를 늘리는 편이
정보량이 크다 — 심의 쟁점으로 남긴다.

**⑤ A4 와 16:9 문서형의 산출이 완전히 동일하다.** 슬라이드 18장·글자 4,338자·상자 383개가
세 무대에서 한 글자도 다르지 않다. 조립기가 무대를 안 보기 때문이다(§5.5 와 같은 지적).
A4 는 세로 1754px 인데 가로 무대와 같은 분량을 싣고 상단 40%만 쓴다 — **A4 전용 분량 규칙**
(장당 불릿 10줄급)이 없으면 A4 는 "16:9 를 세로로 세운 것"에 머문다.

**⑥ 게이트 5 는 무대 이탈을 못 잡는다.** 위 대조군(`g_wide_at43`)에 게이트 4·5 를 돌리면
결과가 **warn 1건뿐**이다 — 그것도 카드 안 텍스트의 `scroll 196x29 > client 192x29` 이고,
씬 5개가 무대 밖으로 310~320px 나간 사실은 리포트에 한 줄도 안 나온다. 원 무대·4:3·A4
세 경우의 게이트 결과가 **완전히 동일**했다.

게이트 5(`gate5_overflow`)가 재는 것은 **요소 내부의 스크롤 넘침**(`scrollWidth > clientWidth`)이고,
**요소가 스테이지 사각형 밖으로 나갔는지**는 재지 않는다. 그래서 §6.5① 의 판정은 게이트가
아니라 별도 DOM 측정(`stage_overflow.py`)으로 해야 했다. 포맷을 새로 만들 때마다 이 측정을
손으로 짜는 것은 낭비다 — **스테이지 경계 이탈 규칙을 게이트 5 에 추가**하는 것이
후속 과제 중 우선순위가 가장 높다(무대가 늘어날수록 손해가 커진다).
